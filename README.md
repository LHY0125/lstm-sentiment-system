# 基于 LSTM 的网络评论情感分类系统

[![License: GPL v3](https://img.shields.io/badge/License-GPLv3-blue.svg)](LICENSE)

基于 LSTM 的中文评论情感二分类系统：PyTorch 训练模型，Flask 提供推理与
可解释性接口，React 前端提供单条分析、批量分析与参数调节。

> 本项目源自河南理工大学计算机学院《神经网络与深度学习》课程设计（选题 3）。
> 课程材料（任务书、报告模板）不在本仓库内。

## 系统组成


| 层     | 目录                     | 职责                                     |
| -------- | -------------------------- | ------------------------------------------ |
| 数据层 | `backend/senti/data.py`  | 语料下载、jieba 分词、词表构建、索引编码 |
| 模型层 | `backend/senti/model.py` | Embedding + LSTM + Linear                |
| 训练层 | `backend/senti/train.py` | 训练循环、网格实验、产物落盘             |
| 推理层 | `backend/senti/infer.py` | 单条/批量预测、遮挡法逐词贡献            |
| 接口层 | `backend/senti/api.py`   | Flask REST 接口                          |
| 前端   | `frontend/`              | React + Vite + Tailwind                  |

前端外观由**三层设计令牌**驱动，全部定义在 `frontend/src/index.css`：
Primitive（原始色阶）→ Semantic（`--background` / `--surface` / `--foreground-*` /
`--border` / `--positive` / `--negative` …）→ Component（`.card` / `.btn` / `.input` /
`.badge` / `.tab` / `.num` …）。**组件里不出现 Tailwind 调色板类**（`bg-slate-800` 之类）
也不出现硬编码色值——换主题只改语义层一处。

令牌到工具类的映射写在 `@theme inline` 里而非普通 `@theme`：后者会把值**静态内联**进生成的
工具类，`.dark` 的覆盖将完全失效（Tailwind v4 与 v3 在这一点上行为不同，是最容易踩的坑）。

明暗两套由 `<html class="dark">` 切换（右上角按钮，选择存 localStorage，首次进入跟随系统），
首帧之前由 `index.html` 内联脚本定色，避免深色用户看到一瞬白屏。
两套主题下正文、次要文字、徽章、提示条与概率条文字的对比度均 **≥ 4.5:1（WCAG AA）**。

训练期离线产出「模型 + 词表 + 元数据」三类产物（`backend/artifacts/`，不入库）；
推理期只消费产物、不做训练，因此换模型等价于换一个 `.pt` 文件。
超参数集中在 `backend/senti/config.py`，训练与推理代码里不出现字面量。

## 数据集

训练语料是**五个互联网评论语料合并后全局重划分**而成，由 `config.CORPUS_PROFILE` 选择
（`"merged"` 是默认值；`"chnsenticorp"` 可退回旧的单语料基线）。合并逻辑见 `backend/senti/corpora.py`。


| 语料                      | 领域                   | 条数      | 积极占比 | 说明                                             |
| --------------------------- | ------------------------ | ----------- | ---------- | -------------------------------------------------- |
| ChnSentiCorp              | 酒店 / 电脑电子 / 图书 | 10 800    | 50.1%    | 主语料，三域合集而非纯酒店域                     |
| `waimai_10k`              | 外卖平台评价           | 11 987    | 33.4%    | 类别偏斜；用语与商品评论差得远（配送/骑手/难吃） |
| `weibo_senti_100k`        | 微博                   | 119 988   | 50.0%    | 社交短文本，风格与其余三个差最远                 |
| `online_shopping_10_cats` | 电商 10 品类           | 62 773    | 50.5%    | 自带品类列（书籍/手机/水果/…）                  |
| `DMSC`                    | 豆瓣电影短评           | 1 650 495 | 77.5%    | 原始 2 125 056 行，由 1–5 星**派生**（见下）    |

**合计 1 856 043 条**，全局随机重划分为训练 **1 670 439** / 测试 **185 604**（10%），
训练集内部再切 10% 作验证集。统一标签约定：**1=积极 / 0=消极**。


| 项                             | 值                                                        |
| -------------------------------- | ----------------------------------------------------------- |
| 训练 / 测试                    | 1 670 439 / 185 604 条                                    |
| 测试集积极占比（= 多数类基线） | 74.3%                                                     |
| 词表大小                       | 20 002（**顶到 `MAX_VOCAB` 上限**；原始不同词数 396 923） |
| 截断长度 MAX_LEN               | 150 词                                                    |

**划分是全局随机切分，不按语料分层**：各语料的类别比例差异极大（DMSC 77.5% 积极、外卖 33.4%），
全局随机切分让三个集合的类别分布一致——这正是「同一分布里切三份」所要求的。

> **⚠️ 偏斜提醒**：测试集 74.3% 是积极，所以**准确率会显著高于模型的真实水平**——
> 无脑全判「积极」就能拿 74.3%。读下面的实测表时，务必与**平衡准确率**和**多数类基线**一起看。

> **DMSC 的两个陷阱**：
> ① 它的原始列是 `Star`（1–5 星）而不是现成的 0/1 标签，二分类由星级**派生**：
> 4–5 星→积极、1–2 星→消极、**3 星丢弃**。3 星占原始数据的 **22.3%**
> （474 559 / 2 125 056 行）——把它硬塞进某一类等于替数据编标签，宁可少要样本。
> ② 它不是「多域」语料：165 万条只覆盖 **28 部 2015 年前后的热门电影**。
> 它带来的是**样本量**，不是领域多样性。

**换语料 profile、或改动任何语料之后必须重训**：`Predictor` 里有 `vocab_size` 一致性断言，
词表与 checkpoint 不同源会在载入期直接失败。

下载与核对：

```powershell
cd backend
..\.venv\Scripts\python.exe -m senti.corpora                 # 下载其余四个扩充语料（约 180 MB）并汇总
..\.venv\Scripts\python.exe -m senti.corpora --no-download    # 只汇总已下载的
..\.venv\Scripts\python.exe -m senti.corpora --keys DMSC      # 只处理某一个
```

数据落在 `数据集/<语料名>/`（已在 `.gitignore` 中，不入库）。

### 演示（单端口）

前端构建一次后，Flask 会顺带托管 `frontend/dist/`，演示时只需一个进程：

```powershell
cd frontend; pnpm build
cd ..\backend; ..\.venv\Scripts\python.exe run_api.py   # 然后直接访问 http://127.0.0.1:5000/
```

该托管路由**只在 `frontend/dist/` 存在时注册**，未构建时接口层的行为与只跑后端时完全一致。
`/api/` 下的路径不会被这条兜底路由吞掉：路径不存在仍是 JSON 404，方法不对仍是 JSON 405（带 `Allow`）。

开发模式（`pnpm dev`）下前端在 5173，`/api` 由 Vite 代理转发到 5000，浏览器看到的是同源请求，
因此**开发期与单端口部署期都不需要 CORS**；后端只对 `/api/*` 放开了白名单里的两个开发源。

## Docker 镜像

镜像**自包含代码与前端**，模型产物由**卷挂载**——这样镜像能从纯仓库重建，
换模型只要换挂载的那份 `.pt`，不必重构。

```powershell
# 构建（多阶段：Node 阶段构建前端 → python-slim 运行时）
docker build -t senti-lstm .

# 运行：把训练产物挂进去（只读即可）
docker run -d --name senti -p 8300:5000 -v "<仓库路径>\backend\artifacts:/app/backend/artifacts:ro" senti-lstm
```

打开 `http://127.0.0.1:8300/`。

也可以直接用编排文件，两份分工不同：

| 文件 | 用途 |
|------|------|
| `docker-compose.yml` | 本地 / 通用：带 `build:`、挂载用相对路径、**只绑回环** |
| `docker-compose.server.yml` | 腾讯云 1Panel：去掉 `build:`（服务器上只 load 镜像）、挂载写**绝对路径**（1Panel 会把编排文件收进自己的目录树，相对路径会跟着跑）、端口**默认只绑回环**（公网直连的写法留在注释里）、**额外限 CPU 并把内存上限提到 1g**（目标机无 swap，OOM 不可挽回，见该文件注释） |

```powershell
docker compose up -d --build      # 走 docker-compose.yml
```

`docker-compose.server.yml` 的头部注释里写了上服务器前要准备的两样东西
（`docker save` 过去的镜像、`/opt/senti-lstm/artifacts/` 里的训练产物）。


| 项         | 值                                                                                                                       |
| ------------ | -------------------------------------------------------------------------------------------------------------------------- |
| 镜像体积   | 约**1.7 GB**（其中 1.2 GB 是 PyTorch）                                                                                   |
| 计算后端   | **CPU**                                                                                                                  |
| 运行时依赖 | **7 个包**（torch / numpy / jieba / flask / flask-cors / requests / pyarrow），清单见 `backend/requirements-runtime.txt` |
| 端口       | 容器内 5000；`HOST` / `PORT` 可用环境变量覆盖                                                                            |

**为什么运行时依赖单独一份清单**：训练要 matplotlib 画曲线、要 pytest，
而推理一行都不用。装进镜像只是白胖几百 MB，所以 `requirements-runtime.txt`
只列被 import 到的包——其中 `requests` 与 `pyarrow` 是经 `infer → train → corpora`
**传递**引入的，不是漏网。

**torch 必须钉 `+cpu`**：Linux 上 PyPI 的 `torch` 默认是 CUDA 构建，会连带拖进
`nvidia-*` 一整套依赖（2.5 GB+）。运行时依赖里写的是 `torch==2.12.0+cpu` 并加了
PyTorch 官方 CPU 索引；万一解析不到，pip 会**报错**而不是静默退回 CUDA 版。

**没挂模型时容器不会崩**：`/api/models` 返回 `[]`、健康检查照样通过。
「没挂模型」与「镜像坏了」是两种状态，必须分得开，所以健康检查**刻意不查模型**。

`docker build` 只需要仓库本身（`数据集/` 185 MB 与 `backend/artifacts/` 都在
`.dockerignore` 里）；`docker run` 时才需要宿主上有一份训练产物。

## 实测结果

> 本表由 `backend/artifacts/meta.json` 生成，与代码实际跑出的一致。
> 顺序即 `GET /api/models` 的返回顺序（按**验证**准确率降序），前端默认选中第一行。

**训练语料**：五个互联网评论语料合并后**全局重划分**（见「数据集」一节）——
训练 **1 670 439** 条 / 测试 **185 604** 条，词表 **20 002**。
测试集里 **74.3% 是积极**，这一点决定了下表该怎么读。


| 模型         | 层数 | 隐藏 | 参数量    | 验证准确率 | 测试准确率 | **平衡准确率** | 训练耗时（本机实测） |
| -------------- | ------ | ------ | ----------- | ------------ | ------------ | ---------------- | ---------------------- |
| lstm_l2_h256 | 2    | 256  | 3,482,370 | 92.39%     | **92.41%** | 88.77%         | 104 min              |
| lstm_l2_h128 | 2    | 128  | 2,824,706 | 92.31%     | 92.34%     | **88.94%**     | 41 min               |
| lstm_l1_h256 | 1    | 256  | 2,956,034 | 92.22%     | 92.15%     | 88.73%         | 63 min               |
| lstm_l2_h64  | 2    | 64   | 2,643,330 | 92.12%     | 92.11%     | 88.51%         | 21 min               |
| lstm_l1_h128 | 1    | 128  | 2,692,610 | 92.11%     | 92.05%     | 88.55%         | 27 min               |
| lstm_l1_h64  | 1    | 64   | 2,610,050 | 91.93%     | 91.91%     | 88.43%         | 16 min               |

**多数类基线 = 74.30%**（对测试集无脑全判「积极」的准确率）。
**最优模型**（按验证集选出）：`lstm_l2_h256`。

### 这三个数字必须一起读

只看 92.41% 会把结论读反——测试集是偏斜的：

- **准确率 92.41% 对基线 74.30%** → 真实增量是 **18 个百分点**，不是 92 个百分点。
- **平衡准确率 88.77%**（两类召回率的均值）不受类别比例影响，是跨语料可比的精度口径。
- 与单语料基线的 89.50% **不可直接比较**：那是在 50/50 平衡测试集上取得的（见下）。

### 与单语料基线的受控对比

为了把「加了数据到底有没有用」变成可回答的问题，做了一次**同一张测试集上的对照实验**：
把旧的 6 个 checkpoint 与新模型**都放在这 185 604 条上评测**。


|                                        | 准确率     | 平衡准确率 | 测试集 OOV |
| ---------------------------------------- | ------------ | ------------ | ------------ |
| 单语料基线（ChnSentiCorp 9600 条训练） | 66.25%     | 62.59%     | 16.38%     |
| 合并语料（167 万条训练）               | **92.16%** | **88.66%** | **5.58%**  |

（六组配置的平均值。OOV 口径为**未截断的 token 级**：对测试集原始分词结果逐词查词表；
若先按 `MAX_LEN=150` 截断再统计，两个数字分别变为 16.42% / 5.57%。）

> **这是一次性对照实验的记录，不是可从本仓库一步复现的产物**：左边一列来自重训**之前**
> 的 6 个 checkpoint（快照留在本机 `backend/artifacts_baseline/`，约 66 MB，**不入库**），
> 右边来自当前 `backend/artifacts/`。两套产物都不随仓库发布，读者需自备才能重跑。

**结论**：提升来自**跨域覆盖**，而不是「数据变多」本身。旧模型在自己语料的测试集上有 89.50%，
换一张多领域混合测试集就掉到 **66.25%**——它学到的是那个语料的分布，不是「中文评论的情感」。
词表 OOV 从 16.4% 降到 5.6%，是这个改善的直接机制。

> 这张表同时解释了为什么两个准确率不能直接比：89.50% 与 92.16% 是在**两张不同的卷子**上考的，
> 差值里混着「卷子换了」这个变量。只有同卷的数字才有差值可言。

### 几点说明

- **排序与默认选中依据验证准确率，不依据测试准确率。** 对 6 个测试准确率取极大值会被系统性高估
  （winner's curse）：那个数字已经被「挑最好」这个过程本身筛过一遍。
- **「训练耗时」是本机墙钟实测值**，不是模型的固有属性——换机器、换批次大小都会变。
- **15 轮明显偏多**：六组的最优轮次都在**第 3–5 轮**，之后一路下滑（如 `lstm_l1_h256` 峰值 92.22% → 末轮 91.54%；逐轮曲线见 `backend/输出/*_curves.png`，未入库）。
  这正是「按验证集选最优轮次」这条纪律的价值——不加它，报告的就是过拟合后的权重。

### 已知局限

**1. 词表顶到上限。** 合并语料的原始不同词数是 **396 923**（建词表时统计并打印，
未单独落盘），而 `MAX_VOCAB = 20000`，
所以词表恰好停在 20 002。测试集因此仍有 **5.58%** 的 OOV。
调大 `MAX_VOCAB` 是一个**待验证**的改进方向——它有代价（低频词的词向量学不准），
需要实测，不能想当然。

**2. 逐词贡献的灰色档分不出「没测到」与「测了没变化」。**
遮挡法把词位改写成 `<unk>` 再前向；若该词**本来就不在词表内**（例如当前的 `江景`），
改写前后序列完全相同，`delta` 恰为 `0.0`——**这次测量是空操作**。
但 `/api/explain` 只返回 `{token, delta}`，不回「该词是否在词表内」，界面因此无法把
「空操作」与「模型确实不敏感」分开，两者落在同一个灰色档里。界面文案只说
「本次遮挡没有产生可分辨的变化」而**不**说「模型认为它中性」。要真正分开需要接口多回一个字段。

**3. 训练集与测试集之间存在文本级重复。** 划分是**按行**随机切、**不按文本去重**：
实测 185 604 条测试行里有 **9.25%（17 169 条）**其文本也在训练集中出现过
（成因是 DMSC 内部的重复短评，如「好看」出现 3684 次，不是跨语料串味）。
它会把测试分数抬高约 **0.09–0.15 个百分点**（92.41% → 约 92.32%）——
量级不大、不影响结论，但确实存在，如实记下；按文本去重是**待验证**的改进方向。

> **一条已消失的误差**：上一版 README 记录过「默认模型把界面的『正面示例』判成消极（0.4234）」。
> 合并语料重训后它**不再出现**：默认模型 `lstm_l2_h256` 现在给出积极 0.9288。
> 那个误差的根因是训练语料单一导致词表覆盖不足——与这次的 OOV 下降是同一件事。
